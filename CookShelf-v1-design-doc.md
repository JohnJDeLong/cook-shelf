# CookShelf — v1 Design Doc

A personal recipe archive that understands food, preserves its history, and adapts it to your needs.

---

## 1. Tech stack & architecture

Opinionated picks, optimized for: shipping v1 in ~4 weeks, low cost, your existing Node/Postgres/Prisma comfort zone.

| Layer | Pick | Why |
|---|---|---|
| Frontend | Next.js 14+ (App Router) + Tailwind + shadcn/ui | One framework for FE + API; shadcn gives you polished components fast |
| Backend | Next.js API routes (or route handlers) | No separate Express server to deploy; you can split later if needed |
| Database | Supabase Postgres | Free tier covers v1; pgvector available later for semantic search |
| ORM | Prisma | Matches your existing skill set |
| Auth | Supabase Auth | Postgres-native, RLS-aware, OAuth + magic link out of the box; consolidated with DB |
| File storage | Supabase Storage | S3-compatible, signed URLs, lives next to the data |
| OCR + recipe parsing | **Claude Vision (single call)** | Image → structured JSON in one shot. Skip the tesseract → cleanup → LLM pipeline entirely |
| Nutrition | Claude estimate for v1; layer in USDA FoodData Central or Edamam later | Estimates are good enough for an MVP and infinitely cheaper |
| Search | Postgres full-text (`tsvector`) for v1; pgvector in v2 | FTS handles "chicken and rice" or "italian dessert under 500 cal" fine |
| Hosting | Vercel (web) + Supabase (DB/auth/storage) | Two providers, generous free tiers; ~$0–25/mo for v1 |

**Architectural principle:** every "AI feature" is a single Claude call with a structured-output schema. No vector DB, no fine-tuning, no agents. Boring is fast.

**Provider consolidation:** Supabase covers DB + Auth + Storage in a single provider. Original plan was Neon + Clerk + Cloudflare R2; collapsing to Supabase reduces wiring on day 1, gives row-level security tied to `auth.uid()`, and keeps recipe images colocated with recipe rows. Tradeoff: Supabase free tier pauses projects after ~1 week of inactivity (one-click resume).

### Volume ↔ weight conversion

Critical for accuracy (especially baking) and for reliable scaling. The approach:

- **Density lives on `Ingredient`, not `RecipeIngredient`.** "All-purpose flour" has the same density everywhere; only quantity changes per recipe.
- **Seed table on day 1** for the top ~100 baking/cooking ingredients (flour, sugar, butter, salt, eggs, common liquids, etc.). King Arthur's ingredient weight chart is a great starting reference; add savory staples from USDA.
- **Claude fallback for unknowns.** When the parser hits an unfamiliar ingredient, ask Claude for `gramsPerCup` (or `avgWeightG` for count items), cache it on the row, mark `densitySource = AI_ESTIMATE`. Pay once per ingredient, ever.
- **Compute `quantityG` at write time**, not read time. Saves doing it on every page load and lets you index/search by weight.
- **Display logic respects `User.unitSystem`.** `MIXED` is the smart default: weight for dry pantry staples, volume for liquids, count for eggs/produce. `IMPERIAL` and `METRIC` do the obvious thing.
- **Scaling math prefers `quantityG`** when present. Multiplying grams is exact; multiplying "1/3 cup" gives you "0.667 cups" which nobody wants to measure.

A reference conversion function (TypeScript-ish):

```ts
function toGrams(qty: number | null, unit: string, ing: Ingredient): number | null {
  if (qty == null) return null;       // unscalable line; show rawText only
  const u = unit.trim().toLowerCase();

  // Already mass
  if (u === "g" || u === "gram" || u === "grams") return qty;
  if (u === "kg") return qty * 1000;
  if (u === "oz" || u === "ounce") return qty * 28.3495;
  if (u === "lb" || u === "pound") return qty * 453.592;

  // By count (eggs, bananas, cloves of garlic)
  if (u === "" || u === "whole" || u === "each" || u === "ct") {
    return ing.avgWeightG ? qty * ing.avgWeightG : null;
  }

  // Volume → grams via ingredient density
  const cups = toCups(qty, u);   // handles cup, tbsp, tsp, fl oz, ml, l, pint, quart
  if (cups != null && ing.gramsPerCup) return cups * ing.gramsPerCup;

  return null;  // can't convert; show original measurement only
}
```

A few notes on the schema:

- **`rawText` on `RecipeIngredient` is the source of truth for display.** Don't try to fully normalize "2½ cups all-purpose flour, sifted" on day 1. Store the raw line; populate `quantity` + `unit` only when the parser is confident; fall back to `quantityText` for fuzzy quantities ("pinch", "to taste", "juice of 1"); render `rawText` verbatim when a line can't be parsed.
- **`quantity` is nullable on purpose.** Real recipes contain "pinch of salt", "salt to taste", "juice of 1 lemon", "1 can crushed tomatoes". Forcing every line into `Float` is the wrong abstraction. Lines without numeric `quantity` are simply unscalable — the UI shows them as-is and the ×2 button leaves them alone.
- **`originalImagePath` is a storage key, not a URL.** Signed URLs expire; the bucket key doesn't. Mint signed read URLs at render time via `lib/supabase/storage.ts`.
- **`User.id` mirrors `auth.users.id` (a uuid).** No `cuid()`. A Postgres trigger on `auth.users` insert creates the corresponding `User` row.
- **`Nutrition.source` is an enum from day 1.** Even if v1 only uses `AI_ESTIMATE`, you'll thank yourself when you add USDA later — no migration needed, just new rows.
- **`DishStory` is its own table, not columns on `Recipe`.** It's regenerable, optional, and you'll probably want to version it later.

## 4. Four-week MVP build plan

The goal: at the end of 28 days, your mom has a real, deployed app she's actually using.

### Day 0 — Pre-flight cleanup (before Week 1)

Settle the three decisions that bite later if you fudge them now:

- Lock `User.id` as `uuid` mirroring `auth.users.id`. Add the trigger that creates a `User` row on auth signup.
- Confirm the **Prisma + RLS posture**: Prisma is the only DB layer; runs as the postgres role; bypasses RLS. App-layer authorization via a `requireUser()` helper is the real guard. RLS is enabled on Storage and as documentation/safety-net on tables. (See §6.)
- Confirm the **async jobs posture**: nutrition and Dish Story are *client-orchestrated synchronous endpoints*, not background jobs. (See §6.)

### Week 1 — Foundation
*Goal: you can manually add and view recipes.*

- **Day 1–2:** Next.js + Tailwind + Prisma scaffold; Supabase project provisioned (Postgres + Auth + Storage); auth wired up (Google + email magic link); the `auth.users` → `User` trigger is in place.
- **Day 3–4:** Migrate the schema; enable RLS + add safety-net policies on user-scoped tables; build a `requireUser()` helper and a scoped query layer (`lib/db/recipes.ts`) that always includes `userId` in `where`. Recipe CRUD route handlers.
- **Day 5–7:** Recipe list page, recipe detail page, manual create/edit form.

✅ Milestone: log in, manually type in a recipe, see it in a list.

### Week 2 — AI ingestion (the magic)
*Goal: snap a photo of a recipe card, get a saved recipe.*

- **Day 8–9:** Image upload to Supabase Storage with signed URLs (bucket: `recipe-images`, scoped to per-user folders via RLS).
- **Day 10–11:** `/api/extract` endpoint — sends image to Claude Vision with a structured-output schema, returns parsed recipe JSON.
- **Day 12–13:** "Review extracted recipe" UI — user confirms/edits before saving.
- **Day 14:** Tag autocomplete + ingredient normalization (basic — match canonical names case-insensitively).

✅ Milestone: photo of grandma's handwritten recipe → structured recipe in DB.

### Week 3 — Search, scaling, nutrition
*Goal: she can find things and double them.*

- **Day 15–16:** Postgres full-text search across title, ingredients, instructions; basic ranking.
- **Day 17–18:** Filter UI — diet, cuisine, course, time, calorie range. Combine with text query.
- **Day 19:** Servings scaler + unit toggle. Pure math on `quantityG` (preferred) or `quantity`. Lines with `quantity = null` (pinch, to taste, etc.) display verbatim and don't scale. Display respects `User.unitSystem`. Seed the top ~100 ingredient densities; wire the Claude fallback for unknowns.
- **Day 20–21:** Nutrition endpoint (`POST /api/recipes/:id/nutrition`, synchronous Claude call). Client fires it after a successful save in parallel with the Dish Story call; UI shows a skeleton until it resolves. Regenerate button hits the same endpoint.

✅ Milestone: "italian vegetarian under 600 cal" works; ×2 button works.

### Week 4 — Dish Story + polish + ship
*Goal: real product, real users.*

- **Day 22–23:** Dish Story endpoint (`POST /api/recipes/:id/dish-story`, synchronous Claude call). Same pattern as nutrition — client fires it after save, UI shows a skeleton, regenerate button hits the same endpoint. Structured into five fields (`culturalOrigin`, `historicalNote`, `regionalVariations`, `servingTraditions`, `funFacts`).
- **Day 24–25:** Source/provenance UI — the SourceType picker, free-text family notes, "digitized from handwritten card" style display.
- **Day 26:** Empty states, error states, loading states. The unglamorous polish week.
- **Day 27:** Mobile pass. Most cooking happens with a phone in the kitchen.
- **Day 28:** Deploy to Vercel (Supabase already lives in the cloud). Give your mom the URL.

✅ Milestone: she's using it.

### Explicitly deferred to v2 (resist the urge)

- Semantic search with pgvector — full-text is plenty for v1
- Nutrition API integration — Claude estimates are fine to start
- Sharing / collaboration / multi-user families
- Meal planning + shopping lists

- Native iOS/Android apps
- Substitution suggestions ("I'm out of buttermilk, what can I use?")

Each of these is great. None are v1.

## 5. Decisions to make before Day 1

1. **Connection pooling mode for Prisma → Supabase.** Supabase exposes both a direct connection and a pgBouncer pooler. Prisma + serverless (Vercel) → use the pooler URL for `DATABASE_URL` and the direct URL for `DIRECT_URL` (migrations need a session connection). Set both env vars correctly and migrations will work.
2. **Single-user vs multi-user UX from day 1.** Schema is multi-user. Auth is multi-user. The only question is whether the UI exposes anything (sharing, households, etc.). *Recommendation: keep it single-user in the UI for v1 — your mom is user #1, you're user #2, and that's the whole beta.*

## 6. Settled architectural patterns

These are decisions that need to be locked before any code is written. Any drift between this section and the rest of the doc should be reconciled here.

### Identity

- `auth.users.id` (uuid, managed by Supabase Auth) is the canonical user identifier.
- Public schema has a `User` table whose `id` is the same uuid.
- A Postgres trigger on `auth.users` insert creates the corresponding `User` row.
- Foreign keys to user (`Recipe.userId`, etc.) are uuid columns referencing `User.id`.
- No `cuid()` for user IDs anywhere.

### Authorization (Prisma + RLS)

We do **not** mix two authorization systems by accident. The chosen pattern:

- **Prisma is the only DB layer for app code** and runs as the postgres role. Postgres role bypasses RLS, so Prisma queries are *not* filtered by RLS.
- **App-layer authorization is the real guard.** Every server action / route handler starts with `const user = await requireUser()` and every query goes through `lib/db/<resource>.ts` helpers that *always* include `userId: user.id` in the `where` clause. Direct `prisma.recipe.findMany()` from a route is forbidden — see AGENTS.md.
- **RLS is enabled on every user-scoped table** with `select`/`insert`/`update`/`delete` policies that check `auth.uid() = userId`. This does *not* fire under Prisma but is documentation/safety-net for any future direct DB access (Supabase JS client, Studio, ad-hoc SQL).
- **RLS *does* fire on Supabase Storage** because the Supabase JS client uses the user's JWT. Storage policies are the real protection on the `recipe-images` bucket — make sure they're correct.

If we ever want Prisma to be RLS-aware, the upgrade path is to switch the `DATABASE_URL` role to `authenticated` and set the JWT per-transaction with `set_config('request.jwt.claims', ...)`. That's a v2 conversation.

### Async work (nutrition + Dish Story)

We do **not** use background jobs in v1. There is no queue, no `waitUntil`, no Inngest, no QStash. The pattern:

1. `POST /api/recipes` saves the recipe synchronously and returns its id.
2. The client fires `POST /api/recipes/:id/nutrition` and `POST /api/recipes/:id/dish-story` in parallel right after.
3. Each is a normal route handler that calls Claude synchronously and writes the result. Each call stays well under Vercel's serverless time limit.
4. The recipe detail page renders skeleton placeholders for both panels until the calls resolve.
5. Regenerate buttons hit the same endpoints.

Tradeoffs accepted: if the user closes the tab between save and the secondary calls, the recipe will be missing nutrition / Dish Story until they revisit the page (where a `useEffect` can lazily call the endpoints if the fields are still null). If we ever outgrow this, the v1.1 swap is to add QStash or Inngest behind the same endpoints.

### Image storage

- Recipe images live in the Supabase Storage bucket `recipe-images`.
- The DB stores the **object key/path** (`Recipe.originalImagePath`), not a URL.
- Signed read URLs are minted at render time via `lib/supabase/storage.ts → signedUrlFor(path, expiresIn)`. Default expiry: 1 hour.
- Storage RLS policies restrict each user to their own folder (e.g. `recipe-images/{user_id}/...`).

## 7. The product story (so you don't lose the plot)

> Most recipe apps store recipes. CookShelf preserves them.
>
> Snap a photo of grandma's handwritten card. CookShelf reads it, structures it, estimates nutrition, tells you the dish's history, and remembers where it came from. Search by ingredient, cuisine, calorie range, or "recipes from grandma." Double it and it does the math. The recipe lives forever.

Pin that somewhere. When you find yourself wanting to build a feature that doesn't serve that sentence, defer it to v2.
